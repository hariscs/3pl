Implement a temporary networking and location check-in architecture for the Lead mobile app.

The app currently uses static data, but it should behave as if it is communicating with a real backend. Build the data layer in a way that dummy JSON files can later be replaced with real API endpoints without changing the screens or feature logic.

Core objectives:

1. Create a reusable networking module responsible for:
   - GET requests
   - POST requests
   - PUT/PATCH requests
   - DELETE requests
   - Request loading states
   - Typed responses
   - Error handling
   - Simulated network delay
   - Optional simulated request failures
   - Future authentication token support

2. Create a repository/service layer between the networking module and the UI.

The UI must never import JSON files directly.

Correct flow:

UI Screen
→ Hook / View Model
→ Repository
→ API Client
→ Mock JSON now, real server later

3. Use strict TypeScript.

Do not use `any`.

Create reusable types for:
   - API response
   - API error
   - Loading state
   - Lead session
   - Location
   - Location bootstrap data
   - Customer
   - Product
   - Employee
   - Load
   - Pay configuration

4. Add a mock API adapter.

The mock adapter should load data from local JSON files and return Promises so the application behaves like it is making real network requests.

Simulate:
   - 500 to 1,000 ms loading delay
   - Successful requests by default
   - Configurable failure mode for testing error states

5. Implement persistent login behavior.

The user should not be required to log in every day.

Persist the authenticated Lead session securely.

On app launch:

- If no authenticated session exists, show Login.
- If the Lead is authenticated but has not checked into a location for the current shift, show Location Check-In.
- If the Lead has an active location check-in, load the saved location dataset and open the Dashboard.
- If a previous active load exists, restore it.

6. Location check-in must be compulsory.

A Lead cannot use Dashboard, Loads, Crew or other operational screens until a location is selected and check-in is completed.

App launch flow:

Splash
→ Restore authenticated session
→ Check active location session
→ Location Check-In if required
→ Download location bootstrap dataset
→ Save dataset locally
→ Dashboard

12. Cache the location bootstrap data locally.

After the bootstrap request succeeds:

- Save the data in application state.
- Persist it locally.
- Make it available across the app.
- Dashboard, Loads, Crew and Start Load should read from this shared location store.
- Do not reload JSON files independently from each screen.

13. Support refresh and synchronization.

Add a `refreshLocationData()` action that requests the bootstrap dataset again and replaces the cached location data.

Display:
- Last updated time
- Refreshing state
- Error state
- Retry action

14. Support offline-style behavior.

If cached location data exists and the mock request fails:
- Continue using cached data.
- Show a non-blocking banner:
  “Using saved location data. Some information may be outdated.”

If no cached data exists and the request fails:
- Show a blocking error state with Retry and Change Location actions.
